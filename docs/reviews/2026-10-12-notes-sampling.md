# Notes highlight continuity sampling

The complete Firefox and WebKit source runs failed the rapid-reversal test's <3px origin assertion with 4.6667px and 6.1633px movement respectively. The assertion sampled before clicking, then awaited Svelte tick and an arbitrary browser frame. That frame is not guaranteed to precede projection playback.

The focused WebKit reproduction in `notes-sampling/timing-investigation.log` records x=85.84375 before the click and x=89.347084 afterward: 3.503334px movement after 45ms elapsed, with the new projection animation already at time 0.040s. Motion's projection starts in its own frame update phase; the test's separate requestAnimationFrame observer can run after that phase has advanced. This is a phase-oracle defect, not evidence of a discontinuity at time zero.

Only the regression test changes. The precise continuity case starts actual projection animations with `autoplay: false`, using a prototype spy scoped to the first rendered example instance because each shared handoff creates a new projection node. It explicitly checks animation time zero before retaining the original <3px origin assertion. Seeking the real animation to 0.08s produces an intermediate pose for the next reversal. The last animation resumes and must settle with one highlight remaining. The second example remains uncontrolled and must preserve its exact node and geometry.

The original natural forward/reverse paint-order test remains unchanged. An additional natural rapid-selection case runs the same five destinations without any clock control, requires more than two interruptions of running animations and more than two intermediate samples, and checks trajectory bounds, label paint order, pointer targeting, focus, button identity, second-instance isolation and final highlight cleanup. Clock-controlled checks therefore do not substitute for natural animation coverage.
